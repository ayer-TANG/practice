## Product One-Liner

把一段聊天记录粘进网页，自动抽出「要做什么 + 什么时候前做完」，按紧急度排好序。

## Problem

微信 / QQ 里的任务靠脑子记。漏掉的往往不是忘了记，而是**从来没意识到那是一条任务**——
没写时间、语气随意、夹在闲聊中间的那种。回头翻聊天记录逐条找又太慢。

现有替代方案都不合适：
- 手动记到待办 App：需要先意识到"这是任务"，漏掉的还是漏掉
- 逐条翻聊天记录：慢，而且没有"紧急度"这个视角
- 大模型方案：要把私人聊天记录发到云端，且这个需求太小，不值得为它搭一套 API 调用

## Primary User

**第一版的目标用户就是产品负责人自己。**

- 技术水平：能打开一个 HTML 文件
- 环境：桌面浏览器（Windows）
- 使用场景：处理完一段聊天后，想快速知道"这段里有什么是我要做的"

**明确不服务**：多人协作团队、移动端优先用户、希望自动接入 IM 的人、需要跨设备同步的人。

## Core Product Object

**任务（Task）**

| 字段 | 说明 |
|---|---|
| 描述 | 要做什么 |
| 截止时间 | 可为空（解析不出时为 `null`） |
| 模糊标记 | `fuzzy`：截止时间来自**约定映射**（如「尽快」→ 今天 23:59）时为 `true`。UI 必须据此标注，见 `SUPPORTED_EXPRESSIONS.md` 第 1.E 节 |
| 紧急度 | **由截止时间派生**，不是独立字段 |
| 来源 | `rule`（规则命中）/ `manual`（用户手动补漏） |
| 原句 | 来源聊天原文，用于核对 |

## Supporting Content

必须存在：

- **原始聊天句子**：作为任务的来源引用。没有它用户无法核对解析是否正确。
- **来源标记**（`rule` / `manual`）：让用户一眼看出哪些是机器找的、哪些是自己补的。

**绝不能变成主产品**：这不是聊天记录阅读器。界面主角永远是任务列表，原文只是附注。

## Main User Journey

```
1. 双击 index.html，浏览器打开
2. 把一个聊天窗口的 ≤10 条消息粘贴进输入区
3. 点「抽取」
4. 看到按截止时间排序的任务列表（含「今晚 21:00 前」这类解析结果）
   + 单独一组「未识别到时间」的任务
5. 对规则漏掉的句子，在补漏输入框手动加进列表；对误检条目一键删除
6. 复制结果到剪贴板 / 下载 .md
```

**价值证明点**：第 4 步——一眼看到「今天要做的」排在最前面。这件事原本要翻聊天记录才能想起来。

## First-Release Scope

必须存在（缺一不可）：

1. 粘贴区（纯文本，≤10 条）
2. 规则抽取：任务句识别 + 时间解析（**相对时间以浏览器当前时间为基准**）
3. 按截止时间排序；无截止时间的任务保留并单独分组排在最后
4. **手动补漏**：把漏掉的句子加进任务列表
5. 误检条目可删除
6. 复制到剪贴板 / 下载 `.md`

## Explicit Non-Goals

| 非目标 | 性质 |
|---|---|
| 持久化 / 完成状态跟踪 | 用户决定（范围排除） |
| 提醒推送 | **当前形态下不可能**：静态页面无法在关闭后提醒，需要后端 + 推送服务 |
| 自动读取微信/QQ 消息 | **当前形态下不可能**：网页无权访问其他应用数据，需要桌面客户端或插件 |
| 推送/导出到 Todoist、滴答清单、日历 | 需要账号授权 + 网络请求，与离线形态冲突 |
| 账号、登录、多人协作、共享 | 范围排除 |
| 后端、数据库、任何网络请求 | 架构排除 |
| 标签、分类、优先级矩阵、任务重要性 | 范围排除（紧急度只有时间一维） |
| 移动端专门适配 | 范围排除（桌面浏览器为首要目标） |

> 前两项不是"我们决定不做"，而是**在当前形态下做不了**。若将来很看重提醒推送，
> 需要重新讨论产品形态，而不是简单加个功能。

## Permissions

- 无认证、无角色、无权限分级
- 无共享、无协作
- 数据不离开浏览器：全部处理在 `index.html` 内完成

## Taxonomy

无标签、无分类、无优先级矩阵。

唯一的分组规则：**有截止时间 / 未识别到时间**，二分。

## Delivery or Download Model

- 交付物：静态文件（第一版为单个 `index.html`，见架构文档的 Open Decision OD-001）
- 获取方式：本地打开；可选托管 GitHub Pages
- 无安装步骤、无付费、无安装包、无后端部署

## Future Extension Points

本版不做，但架构上需要预留：

| 扩展点 | 预留方式 |
|---|---|
| 用 LLM 提升召回率 | 领域层只依赖 `parse(text, now) => Task[]` 契约，LLM 解析器插在同一位置替换规则实现 |
| 持久化 | localStorage 插在领域层之外，领域层不感知 |
| 任务重要性维度 | `Task` 增加字段，`sorter` 增加排序键 |
| 导出到第三方待办 | 交付层新增 renderer / adapter |
| 支持超过 10 条消息 | 结果列表虚拟化（UI 层内部改动） |

## Success Criteria

第一版发布后，以下三条同时成立才算做成：

1. 规则漏掉的任务，能在 **10 秒内**手动补进列表
2. 时间解析正确率 **≥ 80%**（覆盖：今天 / 明天 / 后天 / 周X / 下周X / 今晚 / 明早 / X点前）
3. 闲话（「收到」「哈哈哈」）不干扰；混进来的能**一键删除**

第 2 条的验收依据是 `docs/construction/SUPPORTED_EXPRESSIONS.md`：
**分母只计该文件「支持」列表中的表达**，清单外的不计入。

## Assumption Register

| # | 假设 | 不确定性 | 错了的后果 | 如何验证 | 状态 |
|---|---|---|---|---|---|
| A-001 | 真实聊天里的任务句，大多含可识别的动作词或时间词 | 未用真实数据验证 | 规则召回更低，手动补漏从兜底变主路径 | 拿 10 组真实记录跑一遍 | **部分成立，方向偏弱**（2026-10-09，10 组语料：召回 ≈60%，三组同向） |
| A-002 | ≤10 条规模下解析在浏览器里瞬时可完成 | 未压测 | 需虚拟列表（影响低） | 压测 200 条 | **未验证** |
| A-003 | 以当前时间为基准解析相对时间是够用的 | 隔天回看时会偏 | 时间解析错误，排序失真 | 首次延后使用时复盘 | **未验证** |
| A-004 | 用户愿意接受「手动补漏」这一步 | 依赖使用习惯 | 产品退化为"会漏的自动工具"，价值下降 | 前 3 次真实使用的补漏次数 | **未验证** |
| A-005 | 单个 HTML 文件够用，不需要构建工具 | 代码量未知 | 后期迁移到 Vite，返工成本中等 | v1 完成后评估代码量 | **未验证** |
| A-006 | 裸 `X点` 的 12/24 小时推断规则（D-012）能猜对多数场合 | 「三点」在工作聊天里既可能是 03:00 也可能是 15:00，规则只是启发式 | 部分任务的截止时间偏移 12 小时，排序顺序出错 | 真实数据中统计裸 `X点` 的出现频率与误判率 | **未验证** |

> A-001 与 A-004 是「纯规则 + 手动补漏」这条路的真实风险，不是已解决的问题。
> A-006 是纯规则路线里少数「不是漏检、而是猜错」的风险——猜错比漏检更糟，
> 因为用户看不出哪里错了。真实数据验证时必须单独统计。
> 首版跑通真实数据后必须回来更新本表。

> **A-003 的观察（2026-10-09，F8-6 决策轮，仍不改状态）：**
> A-003 的风险是「以当前时间为基准解析，隔天回看时会偏」。F8-6 正是它的一次**具体显现**——
> 旧规则把已过的月日顺延到下一年，于是**越晚回看，日期偏得越离谱**（偏一整个年）。
> 已按用户决策改为「视为逾期、不回卷」，并在界面标出「已过期」。
> 这只**缓解**了 A-003 的后果（偏离被显式标出，不再静默），但**没有验证 A-003 本身**——
> 真正的验证要等用户延后回看时的实际使用记录。
>
> **A-001 的第二次观察（2026-10-09，Phase 8 词表补齐轮，仍不改状态）：**
> 按真实语料把动作词表从 56 词补到 71 词后，同批 82 行的命中从 44 行升到 66 行，
> 人工标注下召回 ≈90%。**这个回升不能用来更新 A-001，因为没有独立性**——
> 15 个新词就是从这批语料里长出来的。**拿它验证 A-001 等于拿训练集当测试集。**
> A-001 要改状态，需要**第 11 组起的独立语料**复测，并记录召回是否回落。
> 在此之前，状态维持「部分成立，方向偏弱」。
> 依据与逐词数据见 `docs/construction/DEV_PROGRESS.md` 的 Phase 8 词表补齐轮结果一节。
