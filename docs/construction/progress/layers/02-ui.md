# 02 — UI（界面层）

## 状态

**已完成**（Phase 6，2026-10-09；Phase 8 追加「删除上次粘贴」一个控件）。
代码位于 `index.html` 的 `<style id="zhaiwu-style">` 与 `<script id="zhaiwu-ui">` 两块内。

自动化的**渲染/状态验证已建立**（一次性 DOM 桩，见下方「测试」），
但**浏览器中的真实行为仍未验证**——无法在本机启动浏览器，这一点如实记录。

## 职责

- 渲染：粘贴区、抽取按钮、结果列表、「未识别到时间」分组、补漏输入框、删除按钮
- 采集：原始聊天文本；**读取浏览器当前时间并作为 `now` 注入领域层**
- 粘贴记账：记住每次粘贴插进来的那一段，供「删除上次粘贴」整段退回（Phase 8）
- 交互：删除误检条目；手动补漏新增条目；触发交付层（复制 / 下载，Phase 7 接入）
- 补漏后重新调用 `sorter`（不自己写排序逻辑）
- **复制与下载本身属于本层**——它们要碰 `navigator.clipboard` / `Blob` / `URL`，
  只能人工验证。交付层只负责产出 Markdown 字符串

## 硬约束

1. **不得内嵌解析规则**——正则与词表只允许存在于领域层。
   判定标准：本层代码里出现 `/\d+月\d+日/` 这类模式即为违规。
2. **不得自己实现排序**——排序只属于 `sorter`。
3. **零网络请求**——不得有 `fetch`、外部 `<script src>`、CDN 资源、外部字体。
   使用系统字体栈。
4. **必须支持 `file://` 直接打开**——不得依赖本地服务器。
   注意：`<script type="module">` 在 `file://` 下会被 CORS 拦截，**不可使用 ES module 拆分**。
   详见 `ARCHITECTURE.md` 的 D-009。
5. **UI 代码不得写进 `<script id="zhaiwu-domain">` 块**——领域层纯度静态检查
   只扫描该块，混入 UI 代码会让 `document` / `new Date()` 检查失败。

### 关键实现决策

**所有 DOM 都用 `textContent` 构造，不用 `innerHTML`。**
粘贴的聊天记录是用户数据；`innerHTML` 会把记录里的标签当成 HTML 执行。

**手动补的条目跨「抽取」保留。** `runExtract()` 整体替换 `ruleTasks`，
但 `manualTasks` 只增不减。理由是静默丢弃用户自己输入的内容属不良行为。
（产品文档的主用户旅程描述的是单次流程，此选择是在合理默认值上的判断。）

**`Task.id` 不重新生成。** 规则条目的 id 是 `'r' + 原始行号`（领域层 `parse` 生成），
UI 在**同一次** `parse` 调用里直接使用，绝不重新拼接文本再解析——
行号会变，删除操作就跟原文对不上了。

**已知行为（非缺陷）：** 删除某条规则条目后再次点「抽取」，该条目会重新出现。
抽取的语义是「按这份文本重算规则部分」，不是增量状态。

**UI 文案与领域层词表的软耦合：** `fuzzy` 徽章的 `title` 举例了
「尽快 / 马上 / 抓紧」。这是给用户看的说明文案，不参与任何判定；
但领域层若增删紧迫词，这句文案需同步（Phase 8 校准词表时注意）。

### 「删除上次粘贴」（Phase 8，用户直令）

**来源：** 用户指令「第一部分粘贴聊天记录部分能够一键删除上一次的部分」。
Phase 8 的 Excluded 写着「新功能」，本轮之所以做，是因为 `AGENTS.md` 的
Instruction Priority 第 1 条是用户最新明确指令。**这是一次有记录的越界。**

**语义（做之前先定死）：**

- 删的是**一段**，不是全部；连点 N 次按**倒序**逐段删回去
- 只记**粘贴**进来的内容；手敲的字不产生记录（按钮置灰）
- **不是** `Ctrl+Z` 的替代品：原生撤销是逐字的，本按钮是**段级**的——
  粘贴后再在段内改过字，仍然整段删掉

**实现：分两个事件读，因为一个不够。**

`paste` 事件触发时文本框**还没被改写**，此刻的选区就是即将被替换的范围；
插入的结果要等 `input` 事件才读得到。于是 `onPaste()` 只记下
`{before, start, end}`，`onInput()` 再算出
`插入长度 = 新文本长度 − (旧文本长度 − 被替换的选区长度)`。

**定位失败时不猜。** 记账时存了插入起点，但用户之后可能在前方打字，位置会漂。
于是 `locateLastPaste()` 先信位置、再退回「最后一次出现」；两者都对不上
（那段被改得认不出来）就**只给提示、不动文本**，并丢掉这条记录。
静默删错比不删更糟——用户会以为删掉的是这一段，其实动了别处。

**为什么这个按钮放在 UI 层而不是领域层：** 它是编辑动作，不是识别规则。
放进领域层会破坏 `LAYER_CONTRACT.md` 的分层，也会让「领域层纯度」这件事变得含糊。

**已知取舍（非缺陷）：** 若用户手动把已粘贴的整段删掉、而同样的文本又恰好
存在于别处，按钮会删到那处。段级记账无法识别「这段已经不在原位了」，
接受这个代价，不做文本溯源。

脚本从 `index.html` 提取三块 script，领域层与交付层跑在 `node:vm` 中，
UI 块跑在手写的 DOM 桩上，断言渲染结果、状态流转与导出链路

Phase 7 追加：按钮禁用态（空结果 / 交付层缺失）、复制三级链路
（`clipboard` 成功 / reject 回退 `execCommand` / API 缺失）、下载调用与文件名。
Phase 8「删除上次粘贴」追加：**10 组 28 项**（初始禁用、粘一段删一段、
连粘两段倒序删回、全选覆盖式粘贴、前方打字导致位置漂移仍删对、
段内被改过时不静默删错、手敲不记账、空粘贴不记账、同样内容粘两次只删一段、

**这 28 项做过变异检验**：把插入长度的公式故意写错一处（选区长度的符号），
探针**报出 1 项失败**（「覆盖式粘贴」那条）。**探针不是空跑的**——
写测试时若不做这一步，无法排除「断言永远为真」。

**它不进仓库**，因为它测不到真正会出问题的地方（真实浏览器事件、粘贴、CSS 渲染），
却会带来长期维护成本与虚假的覆盖率安全感。它是开发时的探针，不是回归资产。

## 风险

|---|---|
| **浏览器行为未验证** | 桩测试通过不等于浏览器里能用。CSS 布局、真实粘贴（含富文本残留）、触屏点击均未验证。手动清单见上 |
