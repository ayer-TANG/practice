# Master Construction Requirements

顶层施工要求。仅次于用户最新明确指令，高于产品需求与所有其他施工文档。

冻结日期：2026-10-09

---

## 1. 项目目标

交付一个**单文件、零依赖、完全离线**的网页，把聊天记录里的任务抽出来并按截止时间排序。
产品定义见 `docs/product/PRODUCT_REQUIREMENTS.md`，本文件不重复。

## 2. 不可妥协项（Non-Negotiables）

1. **完全离线**。运行时不得发起任何网络请求。不得引入 CDN 资源、外部字体、外部脚本。
2. **零依赖**。不得引入任何 npm 包、第三方库、框架。所有代码自行实现。
3. **零构建**。不得引入打包器、转译器、CSS 预处理器。交付物直接可运行。
4. **双击即用**。用户能在文件管理器里双击打开的 HTML 文件，不得要求启动本地服务器。
5. **数据不出本机**。聊天记录不得离开浏览器进程。
6. **领域层纯度**。领域层不得引用 `document`、`window`、`fetch`、`localStorage`，也不得引用任何 UI 概念。
7. **中文优先**。界面文案、规则词表、测试样例均以中文为准。

## 3. 阶段纪律

- 同一时间只推进 `CONSTRUCTION_PLAN.md` 中的一个阶段。
- 每轮开工前：读 `HANDOFF.md` → 检查 Git → 写 start plan 到 `DEV_PROGRESS.md` → 建 backup 分支。
- 每轮收工前：跑测试 → 修正漂移 → 更新 `HANDOFF.md` → 提交推送 → 如实报告。
- **严格尊重每个阶段的 Excluded 列表**。不得"顺手"实现后续阶段的功能。
- 一个阶段是**有边界的交付物**，不是一个模糊的里程碑。

## 4. 测试纪律

- 未建立的测试一律写 `Not established`。**不得写 `Passed`**。
- 领域层是纯函数，所有解析规则必须有测试用例。
- 失败历史不得抹除：记录首次命令 → 失败结果 → 错误摘要 → 修正动作 → 重测 → 最终结果。
- 每次提交前至少跑：领域层测试 + `git diff --check`。

## 5. 隐私纪律

- **禁止把真实聊天记录写进仓库**。测试样例必须自行编造。
- 文档、日志、提交信息中都不得粘贴真实聊天内容。
- 不得提交密钥、token、账号信息。

## 6. Git 纪律

- 禁止 `git push --force`、`git reset --hard`、`git clean -fd`、`git checkout -- <file>`、`git restore <file>`。
- 纠正错误提交使用 `git revert`。
- 每个阶段开始前必须存在一个**已推送到远端**的回滚点。
- 不覆盖未知改动。发现不明来源的未提交内容时，先停下来问。

## 7. 文档纪律

- 代码与文档必须同时演进。任何行为变更都要同步更新对应文档。
- 不得让仓库比施工文档更真实，也不得让施工文档比仓库更真实。
- 未解决的假设必须写进 Assumption Register，不得藏在自信的叙述里。
- 发现问题但暂不处理时，记入漂移清单或 Open Decisions，不要静默忽略。

## 8. 报告纪律

- 不得伪造测试结果、Git 状态、远端备份或部署成功。
- 只能用三种结论：`Complete` / `Partially complete` / `Blocked`，并说明真实原因。
- 有任一情况成立时不得说"完成"：测试失败、应跑的测试没跑、文档未更新、handoff 未更新、
  该建的回滚点未建、有远端时未推送、存在未解决的用户改动、工作超出约定阶段、实现与产品真值冲突。

## 9. 优先级

```
1. 用户最新明确指令
2. 本文件
3. docs/product/PRODUCT_REQUIREMENTS.md
4. 其他施工文档
5. 现有代码
6. agent 自己的偏好
```
