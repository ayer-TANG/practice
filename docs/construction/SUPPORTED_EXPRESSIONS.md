## 0. 解析语义约定

这些约定使每一条表达都能转成一个确定的时间点，从而可测试。

### 基准时间

所有解析以调用方**注入的 `now`** 为基准。领域层绝不自己读系统时间（见 `LAYER_CONTRACT.md`）。

### 时间粒度 → 具体时刻

| 表达粒度 | 解析到的时刻 | 理由 |
|---|---|---|
| 只给日期（`明天`、`周五`） | 当天 **23:59** | 这一天结束前 |
| 给了时间点（`明天下午三点`） | 该时间点 | 字面 |
| 时间点已过去、且未指定日期（20:00 时说"三点前"） | **次日**同一时间 | 当天已过，说话人指的是下一次 |
| 未指定具体时刻的时段词单用（`下午`） | **不构成时间** | 无法排序，不猜 |

### 周的定义

- 一周从**周一**开始，到**周日**结束
- `周X`（无"这/下"限定）：取 `now` 所在周的该天；**若该天已过，则顺延到下一周**
- `下周X`：`now` 所在周的下一周的该天
- `周末`：约定为**周六**（不区分周六日）

### 一句话多个时间表达

取**最靠左的第一个**匹配，忽略其余。

> ⚠️ 这条只适用于**并列的多个独立表达**（`周五不行的话就下周一`）。
> 它**不**适用于「日期段 + 时间点段」这种组合——那种情况按下一节与 §3 走。
> Phase 8 修订前，两者被混为一谈，见下。

### 日期段自带的时刻是**缺省值**（Phase 8 修订）

§1.A 里 `今晚` `明晚` `明早` `明天早上` 带一个「约定」时刻（晚 = 20:00，早 = 09:00）。
这些表达本质是 **日期段 + 时段词**，约定时刻是**该时段词的默认值**，不是结论：

> 若日期段后面紧跟着一个显式时间点，**显式时间点生效**，约定时刻退为缺省。

这条并非新规则，而是把 §0 已有的两句话还给它本来的适用范围：

- 「给了时间点（`明天下午三点`）→ 该时间点，**字面**」（上面的粒度表）
- 「带时段词者，12/24 制式已由时段词确定」

> **为什么这是一处规格错误（Phase 8 第 2 组真实语料）**：实现把 `今晚`「明早」当成
> `absolute`（已是完整时间点），于是「取最靠左的第一个」让它们把后面**显式写出**
> 的时间点整个吞掉。真实语料里 ——
>
> | 输入 | 修订前 | 修订后 |
> |---|---|---|
> | `活动报名今晚24点截止` | 今天 20:00 | 今天 24:00（= 次日 00:00） |
> | `明天早上8点集合` | 次日 09:00 | 次日 **08:00** |
>
> 前者比真实截止**早 4 小时**，且在 21:30 的 `now` 下已经过去——列表上会显示成逾期。
>
> **三个巧合一直掩盖着它**，三个都是「约定时刻恰好等于显式时刻」，所以断言全绿：
> `明天早上九点`（9:00 == 9:00）、`今晚8点`（20:00 == 8 点）、`下午16:00`。
> 这与 F8-2 是同一个陷阱，因此下面 §1.A 的备注与新测试都刻意使用
> **约定时刻与显式时刻不一致**的例子。

`后天` `大后天` 无时段词，约定时刻本来就是日终 23:59——它们同样收归为日期段，
理由只是与 `明天`/`今天` 保持一致（§3 本就承诺 `[日期段][时间点段]` 成立）。

**期限后缀段（§1.D）不在本节范围内**：§3 的段序是
`[日期段][时间点段][期限后缀段]`，后缀已在末位，其后的时间点不参与组合
（`三天内下午三点交` 仍是 10-12 23:59）。此条已由测试固化，防止扩大化。

### 裸 `X点` 的 12/24 小时推断（Phase 4 补定，D-012）

§1.B 只写了「按上下文推断 12/24 小时制」，没有定义推断规则——那样无法写成测试。
补定如下：

> 裸 `X点`（无时段词）且 `X ≤ 12` 时，候选顺序为
> **今日 X:00 → 今日 (X+12):00 → 次日 X:00**，取第一个**严格晚于 `now`** 的。
> `X ≥ 13` 时按 24 小时制直接用，已过则次日。

例：`now` = 上午 9:00 时说「三点」→ 今日 15:00；`now` = 20:00 时说「三点」→ 次日 03:00。

这是启发式，不是事实——见假设 **A-006**。真实数据验证时要单独统计它的误判率。
「猜错」比「漏检」更难被用户发现，因为列表上看不出哪里不对。

**本推断只在裸 `X点` 单独出现时适用**（Phase 8 补）。若上下文已经给了时段词，
制式由时段词决定，不做跨日推断：

| 输入 | 结果 | 依据 |
|---|---|---|
| `今晚8点开会` | 今天 **20:00** | 时段词「晚」→ 8 读作 8+12 |
| `明天早上8点集合` | 次日 **08:00** | 时段词「早」→ 8 读作 08 |
| `明天8点开会` | 次日 08:00 | 无时段词 → 走本节的跨日推断 |

`今晚` `明晚` 自带「晚」；`明早` `明天早上` 自带「早」。**24 点例外**：
`X ≥ 13` 按 24 小时制直接用，不再修正，所以 `今晚24点` = 今天 24:00 = 次日 00:00。

> **已知风险（Phase 8 如实记录，未修）**：`今晚12点` 这类「12 点表示午夜」的口语
> 习惯，按现行 `h < 12` 的修正门限会读成今天 12:00。这与 `下午12点` 读成正午
> 是同一套约定，本版接受该代价。真实语料里若出现足够频率再决定是否单列。

### 附带时间点的判定（Phase 4 补充，Phase 8 修订）

「日期段」后面紧跟的时间点才算组合的一部分。中间**允许**出现：

- 空格与 `，` `,` `、`
- **一个完整闭合的括号插入语**（≤20 字符），如 `（周三）`、`(本周日)`

`明天下午三点` 是组合；`明天（周三）下午三点` 也是组合——
括号里写星期几是**同位语注释**，不是换了话题。
`明天再说，3点开会` 不是组合——中间隔着的是别的词，只取 `明天`，得到 10-10 23:59。
**未闭合**或**过长**的括号同样视为换了话题，不组合。

> **为什么加括号这一条（Phase 8）**：规格初稿只允许空白与 `，,、`。
> 真实语料里「10月11日（本周日）下午16：00」这类写法很常见，
> 按初稿会把时刻整段丢掉、退回当日 23:59——与本节「给了时间点就用该时间点」直接冲突。
> 这是**规格缺口**，不是实现偏差：实现当时严格照初稿做的。

## 1. 支持的时间表达

### A. 绝对日期

| 表达 | 解析结果 | 备注 |
|---|---|---|
| `今天` `今日` | today 23:59 | |
| `明天` `明日` | today+1d 23:59 | |
| `后天` | today+2d 23:59 | |
| `大后天` | today+3d 23:59 | |
| `今晚` | today **20:00** | 缺省：晚 = 20:00。可被显式时间点覆盖（§0） |
| `明晚` | today+1d 20:00 | 同上 |
| `明早` `明天早上` | today+1d **09:00** | 缺省：早 = 09:00。可被显式时间点覆盖（§0） |
| `X月X日` `X月X号` | 当年该日 23:59；**已过不回卷**，取当年该日（视为逾期） | **已过即逾期**（F8-6，见下方说明） |
| `YYYY年X月X日` | 该日 23:59 | |
| `YYYY-MM-DD` `YYYY/M/D` | 该日 23:59 | **带年份 ⇒ 不回卷**；非法月/日返回 null（F8-10） |
| `X/X` `X-Y` | 当年该日 23:59；**已过不回卷**，同 `X月X日` | 有歧义（`3/5` 可能是分数或比例），v1 接受此代价 |
| `周X` `星期X` `礼拜X` | 本周该天 23:59；该天已过则顺延下周 | 边界必测 |
| `这周X` `本周X` | 同 `周X` | |
| `下周X` `下星期X` `下礼拜X` | 下一周的该天 23:59 | |
| `周末` `这周末` | 本周六 23:59 | 约定：周末 = 周六 |

> **为什么月日不回卷，而 `周X` 回卷（F8-6，Phase 8 由用户决策）**
>
> 两者看着像同一类问题，其实不同：
>
> | 表达 | 已过时 | 理由 |
> |---|---|---|
> | `周X` | **顺延到下周** | 星期是**周期性**的。说「周三交」而今天周四，说话人几乎必然指**下周三** |
> | `X月X日` / `X/X` / `X-Y` | **不回卷，取当年该日（逾期）** | 日期是**一次性的**。真实语料里这类写法大多是通知中**已经发生**的日期，不是待办截止；而「顺延一年」会把它静默改成明年的同一天，**列表上看不出 2026 还是 2027**（A-006 警告的那一类） |
>
> 这条规则改自 Phase 3 的初稿（初稿写「该日已过则顺延到下一年」）。改的依据是
> **10 组真实语料**：本批 58 行里 **40+ 行**被旧规则打中（语料是春季的，`now` 在秋季），
> 三组独立样本都撞到。详见 `DEV_PROGRESS.md` 的 Phase 8 第 3–10 组与 F8-6 决策轮。
>
> **逾期项如何呈现**：`sorter` 是升序，因此已过的日期会**排在最前**（旧规则下它排到最后、
> 显示成明年，反而看不见）。界面上额外加「已过期」标记。
> **注意：Markdown 导出里没有这个标记**——交付层是 `tasks` 的纯函数，没有 `now`。
> 屏幕是「现在」的视图，导出是快照，**这个不对称是有意的**。

### B. 时间点

可与 A 组合，也可单独出现（单独出现时归属"today"或按"已过则次日"规则）。

| 表达 | 解析结果 |
|---|---|
| `上午X点` `早上X点` `早晨X点` | today X:00 |
| `中午X点` | today X:00 |
| `中午` | today **13:00** |
| `下午X点` `晚上X点` | today **X+12**:00（12 小时制 → 24 小时制） |
| `下午3点` 等具体例 | 15:00 |
| `凌晨X点` | today X:00（`凌晨1点` = 01:00） |
| `X点` `X点整` | today X:00；`X ≤ 12` 时按上下文推断 12/24 小时制 |
| `X点半` | today X:30 |
| `X点Y分` | today X:Y |
| `X:XX` `X：XX`（半角/全角冒号） | today X:XX |
| `下午X:XX` `晚上X:XX` `上午X:XX` `中午X:XX` `凌晨X:XX` | 时段词 + 冒号时刻。`下午/晚上` 且 `X < 12` 时 +12，否则照 24 小时制读 |

> **最后一行是 Phase 8 用真实语料补的（规格缺口）**：本表原本分别列了
> 「`下午X点`」（必须带「点」）与无前缀的「`X:XX`」，但没写明两者的交集。
> 实现因此只认前者，真实通知里常见的「10月11日（本周日）下午16：00」整段落空，
> 与 §3「日期段 + 时间点段可组合」的承诺冲突。现补齐并计入 §1 总数（69 → 74）。

> **`YYYY-MM-DD` 那一行也是 Phase 8 补的（F8-10）**：本表原本只有中文写法的
> `YYYY年X月X日` 与无年份的 `X/X`、`X-Y`，没有带年份的数字日期。真实教务通知
> 大量写 `2026-03-20 23:59`，而它整段落空——年份被丢弃，`03-20` 落进无年份模式，
> 在 `now` 已过该日时**顺延到下一年**，于是 `2026-03-20` 被读成 `2027-03-20`。
> **写明了年份反而被忽略**，是静默的错值（A-006 警告的那一类）。
> （「顺延到下一年」这条旧规则本身也已被 F8-6 推翻，见上方 §1.A 的说明。）
> 现补齐，计入 §1 总数（74 → **75**）。

**注意**：时段词必须带具体时刻才有效（`下午三点` ✅）。**单独出现的时段词不构成时间**——
它属于第 2 节「时段词单用」，解析返回 `null`。这是刻意的，不是缺陷。

### C. 期限后缀

不改变解析结果，仅标记"这是截止时间"：

`前`、`之前`、`以前`、`以内`、`内`、`之内`、`前完成`、`前搞定`、`前给我`、`前发我`、`前交`

例：`周五之前` → 与 `周五` 解析结果相同。

### D. 相对期限

| 表达 | 解析结果 |
|---|---|
| `X天内` `X天后` | today+Xd 23:59 |
| `X周后` `X个星期后` | today+7Xd 23:59 |
| `这周内` `本周内` | 本周日 23:59 |
| `下周内` | 下周日 23:59 |
| `这个月内` `本月内` | 本月最后一天 23:59 |
| `X个工作日` `X个工作日内` | today 起算 X 个工作日（跳过周六日）的 23:59 |

### E. 紧迫词 —— 约定映射

| 表达 | 解析结果 |
|---|---|
| `尽快` `马上` `抓紧` `赶紧` `第一时间` `立刻` `马上就好` | today 23:59，标记 `fuzzy = true` |

**这是约定，不是字面含义。** 理由：

产品紧急度只有时间一维（D-004）。若把"尽快"归为"无截止时间"，它会排在列表最后 ——
与直觉相反。映射到"今天 23:59"既保留了紧迫性，又不凭空发明具体时刻。

因此 `Task` 增加 `fuzzy: boolean` 字段。UI **必须**据此标注（如显示"尽快（按今天算）"），
不能让用户以为这是对方说的明确时间。这是诚实性的要求，不是可选装饰。

## 2. 明确不支持

以下表达**不计入成功标准 2 的分母**。它们出现在真实聊天里时，
解析器返回 `null`，任务落入"未识别到时间"分组 —— 由用户手动处理。

> **实现要点（Phase 4 发现）**：本表里有几条**含有受支持的片段**——
> 「上周三」含「周三」、「下下周三」含「周三」、「3点5分8秒」含「3点5分」。
> 若只按 §1 的模式正向扫描，它们会被误解析成时间，违反「必须返回 null」。
> 因此实现采用**先屏蔽、再解析**：命中本表的区域先被替换为空格，之后才扫描。
> 详见 `progress/layers/01-domain.md`。

| 类别 | 例子 | 为什么不支持 |
|---|---|---|
| 双重相对星期 | `下下周三`、`下下个星期` | 组合爆炸的起点，真实频率低，收益不划算 |
| 模糊区间 | `下个月`、`月中`、`中旬`、`月底`、`月末`、`季度末` | 无明确日期，需要业务约定才能落地 |
| 迟滞词 | `过几天`、`改天`、`有空时`、`找时间`、`回头`、`这阵子`、`最近` | 本质是"时间未定"，不是"时间未知" |
| 过去的表达 | `昨天`、`前天`、`上周三`、`上次` | 作为**截止**时间无意义（这是已完成/已逾期的追责，不是待办） |
| 农历与传统节日 | `农历八月十五`、`春节前`、`国庆前`、`中秋前` | 需要农历表，v1 不引入 |
| 月份时长 | `X个月后` | 月末对齐规则复杂（1月31日 + 1个月 = ?），收益低 |
| 时段词单用 | 单独一个 `下午`、`晚上`、`上午` | 无具体时刻，无法排序 |
| 精确到秒 | `X点X分X秒` | 真实聊天几乎不出现 |

## 3. 组合上限

解析器按 **`[日期段] [时间点段] [期限后缀段]`** 三段匹配，**每段最多一个**。

**支持的组合：**

| 例子 | 命中的段 |
|---|---|
| `明天下午三点前` | 日期 + 时间点 + 后缀 |
| `下周三上午十点` | 日期 + 时间点 |
| `周五之前` | 日期 + 后缀 |
| `今天内` | 日期 + 后缀 |
| `3个工作日` | 相对期限 |
| `尽快` | 紧迫词 |

**不支持的组合：**

| 例子 | 原因 |
|---|---|
| `下下周三下午两点半前` | 日期段是双重表达（`下下周三`） |
| `明天早上九点前或者后天都行` | 一句话两个时间 → 取最左的第一个（`明天早上九点`），另一个被忽略 |
| `三天内下午三点交` | 期限后缀段已在末位，其后的时间点不参与组合（§0 末段） |

> ⚠️ 上面第一条例子的**结果值 `09:00` 是巧合**：`明早` 的缺省时刻恰好也是 09:00，
> 所以它在 Phase 8 修订前后都是 09:00，掩盖了「显式时刻 `九点` 被丢弃」这件事
> （见 §0「日期段自带的时刻是缺省值」）。该断言本身仍然有效，保留。

### 紧邻规则（Phase 4 补定）

`下下周三下午两点半前` 这一条需要额外说明：它由「被否决的日期段」+「受支持的时间点」
拼成。屏蔽掉 `下下周三` 之后，剩下的 `下午两点半` 单独看是合法的，
会被解析成**今天**的 14:30 —— 这显然是错的。

因此补定：

> 若选定候选**紧贴在被屏蔽区域之后**（中间无任何字符），说明它是被否决表达的一部分，
> 整体返回 `null`。

反例（**不**触发本规则）：`下下周三，明天给你` —— 屏蔽区与候选之间有 `，`，
说明是两个独立表达，返回 `明天` 的时间。

本规则是 Phase 4 实现时发现的、原文档未写明的推论，故补记于此。

| 交付推进 | 提交、上传、发、回复、确认、处理、安排、完成、跟进、核对、整理、更新、准备、修改、检查、落实、对接、审批、同步 |
| 截止 | 截止、deadline、之前给我、之前发我 |

**Phase 5 新增（18 个）**

| 类别 | 词 | 依据 |
|---|---|---|
| 紧迫 | 尽快、马上、抓紧、赶紧、第一时间、立刻 | **直接取自 §1.E 已冻结的紧迫词清单**，不是新判断。含这类词的句子必然在说一件要做的事；缺了它，「尽快把环境搭好」会整句漏掉，§1.E 的紧迫映射永远没机会生效 |
| Phase5补充 | 开会、会议、汇报、参加、报名、签到、出差、报销、缴费、预约、取件、反馈 | **判断，不是数据**。工作/学习聊天里近乎无歧义的「有件事要做」标记，「周三下午开会」这类句子原本会被整句漏掉。待 Phase 8 用真实语料校准，**可能增也可能删** |

**合计 56 个。** 测试里有对 38 / 56 的断言。

### 反向 —— 不得判定为任务

`收到`、`好的`、`好`、`嗯`、`哦`、`明白了`、`了解`、`没问题`、`辛苦了`、`谢谢`、`谢了`、
`哈哈`、`哈哈哈`、`在吗`、`早`、`早安`、`晚安`、`已阅`、`OK`、`ok`、`嗯嗯`

**共 21 个，测试里有断言。**

反向用例的重要性不亚于正向：识别类功能最常见的失败是**误检**而非漏检。

### 反向规则的匹配范围（Phase 5 定，关键）

反向词按**整行**匹配，**不是子串**。剥掉标点与空白后若被反向词完全吃光，才算寒暄。

理由：「收到，明天发你」含「收到」，但它是个真任务。用子串匹配会把它误杀。

```
「收到」            → 不是任务（整行被吃光）
「好的好的」         → 不是任务（反复剥离后吃光）
「收到，明天发你」    → **是**任务（剥剩「明天发你」，命中「发」）
「好的，我明天处理」  → **是**任务（剥剩「我明天处理」，命中「处理」）
```

### 已知漏检（召回缺口，Phase 5 记录）

规则路线的另一面。与 §5 不同 —— §5 是"识别错了"，这里是"没识别出来"。
同样不是待修的 bug，是固有边界；Phase 8 统计其频率以更新 A-001。

| 例子 | 为什么漏 |
|---|---|
| `下周三上午十点开个复盘会`、`明天开个短会` | 词表里是「开会」，而口语总把它拆开说（开个…会） |
| `周五之前给你答复` | 「答复」不在词表内 |
| `把那个东西弄一下` | 口语化交付说法，无法穷举 |

**在 Phase 8 拿到真实语料的频率之前不补词**——「不得凭感觉写规则」是本项目明文约束。
测试里这三条被断言为 `false`，锁定现状：将来若补齐，测试会红，提醒同步本文件与 A-001。

## 5. 已知误检风险（纯规则无法解决，如实记录）

这些不是"待修的 bug"，是**纯规则路线的固有边界**。
Phase 8 必须量化它们在真实数据中的出现频率，据此更新假设 A-001。

> 本节是**误检**（把不是任务的判成任务）。**漏检**（把任务漏掉）记在 §4 末尾。



| 类型 | 例子 | 为什么规则做不到 |
|---|---|---|
| 已完成的任务 | 「我已经提交了」「昨天就发你了」 | 含动作词，但已完成。纯规则判不了时态 |
| 他人的任务 | 「他说他会处理」 | 动作词属于第三方，既不是说话人也不是你 |
| 条件式 | 「如果周五还没好就找我」 | 有前置条件，不一定是当前任务 |
| 否定式 | 「不用发了」「别提交」 | 含动作词，语义相反 |
| 反问 | 「这个什么时候能好？」 | 表面是问句，实际可能在推进任务 |

**这些正是「手动补漏 + 一键删除」这个产品定位存在的原因。**
不要在实现时试图用更复杂的规则消灭它们——那是 LLM 的活，不是正则的活。

## 6. 验收方式（成功标准 2）

```
正确率 = 解析结果与人工判定一致的表达数 / 清单内出现的表达总数
```

规则：

1. **分母只计第 1 节「支持」列表中的表达**
2. 第 2 节「不支持」列表中的表达出现在语料里时，**单独统计数量**，不计入正确率
3. 人工判定基准 = 本文件第 0 节的语义约定是否被正确执行
4. 目标：**≥ 80%**

**这条度量规则本身就是约束**：若把不支持的表达也算进分母，正确率必然低于 80%。
度量时必须先分类，再计算。不得含糊。
